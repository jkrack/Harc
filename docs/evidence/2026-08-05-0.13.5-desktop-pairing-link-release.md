# Harc 0.13.5 Desktop pairing-link release

**Date:** 2026-08-05

**Status:** Published through the notarized GitHub release and live Sparkle
update feed.

## User-facing defect

The Host successfully created a pairing ticket and rendered its QR code, but
the waiting state looked like link creation was still running. A secondary Mac
without a usable camera had no explicit way to move the short-lived ticket into
the Client flow.

## Resolution

- The Host now distinguishes **Pairing code created** from the subsequent wait
  for a Client claim, shows a live expiry countdown, and can create a replacement
  ticket without racing cancellation of the prior reservation.
- The Host offers **Copy Pairing Link** and the Client offers **Paste Pairing
  Link**. Pasted values remain bounded to the canonical `harc-pair://v1/` wire
  format before decoding or opening a connection.
- Copying is explicit and warns that Universal Clipboard or messaging can move
  the temporary secret through a cloud service. QR scanning remains the
  preferred local-only transfer.
- Copy/paste does not weaken protocol approval: the ticket is still short-lived,
  single-use, TLS-pinned, bound to the Host authority, protected by four-word SAS
  comparison, and requires foreground Host scope approval.

## Remaining physical acceptance

Update both Macs to 0.13.5, copy a fresh Mac-client link on the Host, paste it
on the Client, compare the four words, approve the requested scopes, and then
complete the real Client capture/upload/receipt/Host-processing flow. This
release removes the missing desktop transfer surface; it does not itself claim
that the physical PR 9 acceptance gate is complete.
